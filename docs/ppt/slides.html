02 / 架构

三层结构，客户端不碰数据库

页面层
15 个页面 · pages/*
只做渲染与交互，无业务逻辑
服务层
services/* + utils/api.js
唯一网络出口，统一拆包 {ok, data}
云函数
cloudfunctions/api · 38 action
身份校验 / 业务校验 / 写库
数据层
云数据库 + 云存储
安全规则：客户端读写全部关闭

为什么这么切

小程序端的 openid 由微信下发，但客户端代码可被反编译。

因此身份判定、封禁校验、写权限全部下沉到云函数，数据库安全规则对客户端读写一律关闭。

客户端只剩一个出口：utils/api.js。

03 / 选型

为什么是云开发，而不是自建服务器

自建服务器

  • 部署 / 域名 / HTTPS 证书
  • 登录态与 openid 换取
  • 数据库运维与备份
  • 按量计费，前期就要花钱
  • 至少多花 1 周在环境上

微信云开发

  • 免运维，随小程序一起发布
  • getWXContext 直接给 openid
  • 托管数据库 + 安全规则
  • 免费额度够课程设计用
  • 把时间花在业务逻辑上

代价：云存储免费版是「仅创建者可读」，图片只能转 base64 入库——后面会提到。

05 / 案例 · 根因

学号被写进了 openid 字段

chats.openidA = "000000003" ← 这是学号 goods.sellerOpenid = "000000000" ← 这也是学号 users 按 openid 查 → 查不到 → 昵称回退成字面量「卖家」

真实 openid 形如 obfA_3VuO7m9tS-…，永远不会是纯数字。
历史版本的一部分代码把 sid 直接写进了 openid 字段，
于是会话的「对手方」指向了一个根本不存在的用户。

一条会话没有主人 —— 消息写进去，谁都收不到。

怎么查出来的

1　写一个只读自检接口
　 只返回调用者本人的数据

2　用两个账号各跑一次
　 对比 chats / users / goods

3　把 sid 反查 users
　 发现「卖家」其实是同班同学

05 / 案例 · 方案

一对用户，只能有一条会话

const pairKeyOf = (a, b) => { const [x, y] = a < b ? [a, b] : [b, a]; return 'c_' + md5(x + '|' + y).slice(0, 24); };

历史数据怎么办

迁移脚本：先预演（只读），确认后再执行；旧会话只打标记，一条消息都不删。

确定性主键 会话 id 由两个 openid 算出，写死在服务端，并发也造不出第二条。
主键即约束 add 相同 _id 会被数据库直接拒绝，不依赖「先查后插」这类有竞态的写法。
商品降级为上下文 goodId 不再进主键，改为会话内 currentGoodId + 每条消息的 goodId。

06 / 设计

安全上的三个边界

身份边界

openid 只从 getWXContext 取，客户端传什么都不信。

const { OPENID } = cloud.getWXContext();

数据边界

所有写操作经云函数；数据库对客户端一律读写关闭。

{ "read": "doc.openidA == auth.openid", "write": false }

管理边界

admins 表 + 服务端常量双判定；控制台与个人会话完全隔离。

adminOf(openid) → requireAdmin()
