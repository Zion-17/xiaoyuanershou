02 / 架构

四层结构，客户端不碰数据库

页面层
15 个页面 · pages/*
只做渲染与交互，无业务逻辑
服务层
services/* + utils/api.js
唯一网络出口，统一拆包 {ok, data}
云函数
cloudfunctions/api · 38 action
身份校验 / 业务校验 / 写库
数据层
云数据库 + 云存储
安全规则：客户端读写全部关闭

为什么这么切

小程序端的 openid 由微信下发，但客户端代码可被反编译。

身份判定、封禁校验、写权限全部下沉到云函数，数据库安全规则对客户端读写关闭。

客户端只剩一个出口。

02 / 代码

客户端只有一处碰网络

utils/api.js
1function call(action, payload = {}) {
2  return new Promise((resolve, reject) => {
3    wx.cloud.callFunction({
4      name: "api",
5      data: { action, payload },
6      success(res) {
7        const r = res && res.result;
8        if (r && r.ok) resolve(r.data);
9        else reject({ code: r.code, message: r.message });
10      }
11    });
12  });
13}

为什么只留一个出口

服务端统一返回 { ok, data } / { ok:false, code }。

拆包只发生一次，「错误码 → 提示文案」只需维护一份。

新增接口不用重写错误处理。

03 / 根因

学号被写进了 openid 字段

数据库真实数据（已脱敏）
1chats.openidA      = "000000003"   // 学号，不是 openid
2goods.sellerOpenid = "000000000"   // 同样是学号
3users 按 openid 查  ->  null
4昵称回退成字面量「卖家」  // 头像也一起丢了

怎么查出来的

1　写只读自检接口
　 只返回本人数据

2　两个账号各跑一次
　 对比 chats/users/goods

3　sid 反查 users
　 发现「卖家」是同班同学

真实 openid 形如 obfA_3VuO7m9tS-…，永远不会是纯数字。历史代码把 sid 直接写进了 openid 字段，会话的「对手方」指向了一个不存在的用户——
一条会话没有主人，消息写进去，谁都收不到。

03 / 方案

一对用户，只能有一条会话

cloudfunctions/api/actions/chat.js
1const pairKeyOf = (a, b) => {
2  const [x, y] = a < b ? [a, b] : [b, a];
3  return "c_" + md5(x + "|" + y).slice(0, 24);
4};
5
6const chatId = pairKeyOf(openid, good.sellerOpenid);
7let chat = await getChat(chatId);
8// 同 _id 的 add 会被数据库直接拒绝
确定性主键

会话 id 由两个 openid 算出，写死在服务端。

主键即约束

并发也造不出第二条，不依赖「先查后插」。

商品降级为上下文

goodId 不再进主键，改为 currentGoodId。

迁移脚本先预演再执行；旧会话只打 mergedInto 标记，消息一条不删。
